# 项目方案工作流

> 本文件为 `solution-expert` 的**项目方案**处理模块。按需加载，仅在入口分流命中"完整"或"精简"路径时由主 Agent Read。
>
> 涉及 5 大场景：**新增 / 修改 / 优化 / 重构 / 移植**。

---

## Step 1 · 调研项目上下文

在动笔之前，必须先理解项目。并发起：

1. `Glob` —— 摸清目录结构、模块划分、构建产物
2. `Read` —— 阅读 `README.md`、`package.json`/`pom.xml`/`go.mod`/`Cargo.toml` 等元信息
3. `Grep` —— 找与本次需求相关的核心文件、已有约定、命名风格
4. 必要时 `Bash` 运行只读命令（如查看 Git 最近改动、依赖版本）

### 调研证据台账（设计输入闸门）

只登记会影响**范围、选型或 DoD** 的关键结论；小型任务可只列 1-3 行：

| 关键结论 | 状态 | 证据 / 待确认来源 | 证据时间锚 | 对范围、选型或 DoD 的影响 |
|----------|------|------------------|------------|--------------------------|
| ... | 已验证 / 假设 / 未知（阻塞/非阻塞） | `path:line`、命令输出摘要或用户明确陈述 | commit SHA / 日期 / 版本号 | ... |

- **已验证**：必须可定位；文件引用、配置、命令输出摘要或用户明确陈述均可作为证据
- **证据时间锚**：每条证据同时标注 commit SHA（首选）/ 提交日期（次选）/ 仓库版本（退路）之一；调研完成时强制填写，禁止"待补"；漂移即回到 Step 1 重取证并更新台账
- **假设**：明确标注待验证，不得写成项目现状
- **未知**：必须标注阻塞性；只有缺失答案会改变推荐方向或 DoD 时才标"阻塞"
- **阻塞项关闭方式仅三种**：补充证据验证、用户明确决策、用户明确授权 agent 采用默认值；第三种必须登记默认值、理由与可逆点
- 未关闭的阻塞项不得进入 Step 3；非阻塞项可保留到方案的假设 / 开放项中

**移植类场景额外调研**：

- **源项目**：被移植功能所在项目的模块边界、依赖图、相关代码入口
- **目标项目**：目标项目的同名/相似模块、依赖版本、构建配置、UI 容器
- **差异清单**：两边在语言/框架/版本/目录约定上的差异，识别兼容点与冲突点

### 安全与数据分类前置（命中即触发威胁建模）

调研阶段识别本次方案涉及的数据分类，作为安全设计是否强制的闸门：

| 分类 | 示例 | 是否触发威胁建模 |
|------|------|----------------|
| 公开 | 文档、图片 | 否 |
| 内部 | 日志、配置 | 否 |
| 敏感 | 身份证、银行卡、手机号、生物特征、未成年人数据 | ✅ 必填威胁建模 + 联动 security-review |
| 受监管 | 医疗、金融、跨境、行业法规管辖数据 | ✅ 必填威胁建模 + 联动 security-review |

未命中敏感或受监管数据时，`§3.2 安全设计` 可写"无（无敏感数据）"，精简路径下可直接跳过。命中后必须联动 security-review skill 完成独立安全评审，并将结论写回方案的"安全设计"章节。命中敏感或受监管时，主 Agent 必须打印 `🔗 联动 security-review（命中敏感数据），等待用户确认` 并阻塞下一步；该联动**不参与去抖**（详见 SKILL.md §跨 skill 联动粒度与去抖规则）。

调研结束时，用 3-5 行摘要告知用户你对项目的理解。ack 规则按入口路径执行：

- **完整路径**：必须输出下行并让用户确认或纠正；ack 后进入 Step 2，不通过则回到 Step 1
- **精简路径**：仅证据台账仍有阻塞项时请求 ack；无阻塞项可直接继续

> ```
> ✅ 已读懂需求：<1-3 句话概括用户的需求和约束>
> ```

## Step 2 · 澄清关键决策

禁凭空假设。先逐项检查下列七个维度，再用 AskUserQuestion 一次性收集**尚未被用户输入或仓库证据覆盖、且会改变推荐方向或 DoD** 的缺口：

- **需求编号化（必填）**：完成六维澄清后输出一份需求清单 `R1 / R2 / ...`，每条需求包含：描述、验收口径、关联用户/系统角色。后续 §3.1 文件变更、§6 测试要点、§8 可追溯矩阵必须引用同一 `R-N` 编号。

- 已覆盖的维度不重复提问，在调研证据台账中引用即可
- 未覆盖但非阻塞的维度可用显式假设继续，并在方案中保留开放项
- 用户已授权"你来决定"时可采用默认值，但必须登记选择理由和可逆点

- **范围**：本次方案涉及哪些模块/服务/接口？哪些明确不在范围？
- **目标**：业务目标是什么？非功能性目标（性能/可用性/兼容性）？
- **约束**：必须保留的兼容点？禁止使用的依赖？上线时间窗？
- **移植一致性**：哪些维度必须保持一致（数据/语义/轮询/UI/接口）？哪些允许本地化调整？
- **NFR 量化**：性能（QPS/P99/容量）、可用性（SLA）、安全（合规要求）、可观测性、可维护性
- **MVP 与 DoD**：最小可发布切片是什么？Definition of Done 如何定义？谁来验收？

## Step 3 · 设计与对比

- **统一比较口径**：候选必须共享同一问题目标、现状基线、交付时间窗、成本范围和设计粒度，禁止用粒度差制造稻草人
- **先过可行性闸门**：逐项检查用户禁止项、版本/技术兼容、上线窗口、合规、安全、预算上限；否决依据引用调研证据台账
- 候选状态仅用 **可行 / 淘汰 / 基线**；淘汰项保留否决证据但推荐度记 `N/A`，不得参与评分
- 完整路径以 **2-3 个可行方案**为目标；精简路径至少比较"实施"与"维持现状"
- 维持现状 / 延后可作为机会成本"基线"，但不自动计入可行技术方案数
- 客观仅一项可行时不要凑数：逐项列出其他候选的硬约束证据，并披露集中决策、供应商锁定或未来替换成本；架构师评审仍只沿用既有触发条件
- 只在可行项之间用对比表呈现目标收益、架构影响、依赖成本、实施复杂度、风险与可回滚性
- **明确给出推荐方案与理由**，不要罗列后让用户自己选
- 推荐方案必须包含：模块划分、关键接口/数据结构、流程图/时序图
- 移植类场景需额外说明：**哪些保持一致、哪些本地化适配、为什么这样切分**

## Step 4 · 三阶段流水线（草稿 → 审核 → 优化 → 终稿）

按顺序执行，每一步不可跳过（除非命中"跳过路径"）。

> **与评审分级的边界**：§方案评审分级与触发表 决定是否增加人工 / 架构师 / RFC 评审，不改变本节质量门。完整路径即使判为"免审"也必须走草稿 → 审核 → 优化；只有下方"何时跳过审核与优化"明确列出的路径可裁剪。

### Step 4.1 · 生成草稿

- 按前面 Step 1-3 的产出生成完整方案草稿（沿用标准 8 章模板）
- 落盘到 **`.scheme/temp/<name>-draft-<yymmdd>.md`**（temp 目录不存在则自动创建）
- 输出草稿时同步打印一行：`📝 草稿已落盘：.scheme/temp/<name>-draft-<yymmdd>.md`

### Step 4.2 · 审核助手（subagent）

- `Read references/review-template.md` 拿到完整契约（subagent 类型 / 行为约束 / 报告模板 / prompt 模板）
- 启动 `general-purpose` subagent，按 `references/review-template.md §6` 的 prompt 模板组装输入
- subagent 严格按"审核报告模板"输出，**不改草稿**
- 落盘审核报告到 **`.scheme/temp/<name>-review-<yymmdd>.md`**
- subagent 返回空 / 非结构化 → 主 Agent 重试 1 次，仍失败则报告用户并询问是否跳过审核
- 审核结束后打印一行：`🔍 审核报告已落盘：.scheme/temp/<name>-review-<yymmdd>.md`

### Step 4.3 · 优化助手（subagent）

- `Read references/optimize-rules.md` 拿到完整契约
- 启动 `general-purpose` subagent，按 `references/optimize-rules.md §6` 的 prompt 模板组装输入
- subagent 逐条评估审核建议（**采纳 / 部分采纳 / 不采纳**），不采纳必须给出理由
- subagent **只采纳审核报告中的建议**，不新增审核没建议的内容
- 产出最终方案（含"修改追溯表"附录），落盘到 **`.scheme/<name>-<yymmdd>.md`**
- 优化结束后打印一行：`✅ 最终方案已落盘：.scheme/<name>-<yymmdd>.md`

### Step 4.4 · 主 Agent 收尾

- 检查最终方案中的"修改追溯表"是否与审核报告的每条建议**一一对应**
- 输出用户摘要（包含 `.scheme/temp/` 与最终方案的路径）
- 询问用户是否保留 temp 产物（默认保留 30 天可清理）
- 输出收尾确认行：`🏁 方案流水线完成 | 最终:.scheme/<name>-<yymmdd>.md | temp:<草稿+审核报告路径>`

### 何时跳过审核与优化

| 场景 | 是否走审核 | 是否走优化 | 理由 |
|------|-----------|-----------|------|
| 新增 / 修改 / 优化 / 重构 / 移植（完整方案） | ✅ 必走 | ✅ 必走 | 价值最高 |
| 精简路径 | ❌ 默认跳过；用户明确要求完整质量门时必走 | 同左 | 路由已限定为低风险小改 |
| Bug 修复类请求 | ❌ 跳过 | ❌ 跳过 | 排除在 skill 边界外 |
| 用户明确说"先出草稿我自己看" | ❌ 跳过 | ❌ 跳过 | 显式 opt-out |

## 精简路径最小字段集

> 命中精简路径后，按下表的"必填 / 可缩写 / 可删除"三档裁剪 §1-§4；**NFR 量化、风险 owner、回滚触发条件三项不得裁剪**。总行数硬上限 5-10 行。

### §1 背景与目标

| 字段 | 档 | 精简下处理 |
|------|----|----------|
| 背景（一句话） | 必填 | 保留 1 行（不超过 30 字） |
| 目标（量化） | 必填 | 保留 1 行（带具体数字或 N/A） |
| 范围 / 不在范围 | 可缩写 | 合并为 1 行 "范围：X / 不做：Y" |
| DoD 验收 | 必填 | 保留 1-2 行 bullet |
| §1 NFR 量化 | **不可裁剪** | 即使精简也要保留一行 |

### §2 方案对比与选型

| 字段 | 档 | 精简下处理 |
|------|----|----------|
| 候选对比表 | 可缩写 | 缩为 1 行 |
| 选型结论 | 必填 | 保留 1 行 |
| ADR 完整模板 | 可删除 | 精简下用 1-2 行简化 ADR |

### §3 详细设计

| 字段 | 档 | 精简下处理 |
|------|----|----------|
| 模块与文件 | 必填 | 保留 1 行 |
| 关键接口 / 数据结构 | 可缩写 | 仅在变更 / 移植场景必填 |
| 流程图 | 可删除 | 精简下省略 |
| 安全设计 | 可删除 | 仅当无敏感数据时可省 |

### §4 风险与缓解

| 字段 | 档 | 精简下处理 |
|------|----|----------|
| 风险项 | 必填 | 至少保留 1 行 |
| 风险 owner | **不可裁剪** | 即使精简也要标注 owner |
| 触发到响应时间窗 | 可缩写 | 合并到风险那一行 |

### §5 回滚策略

| 字段 | 档 | 精简下处理 |
|------|----|----------|
| 触发条件（量化） | **不可裁剪** | 至少 1 行 |
| 回滚步骤 | 必填 | 保留 1-2 行 bullet |
| Feature Flag 名 | 必填 | 保留 flag 名 + 默认值 |

### 精简骨架示例

```markdown
# <标题>（精简骨架）
- 背景：X；目标：Y（量化）
- 范围：改 A 文件 +N 行 / 不做：B
- 推荐方案 A：<一句话核心思路>
- 主要风险：X（owner：团队+角色），缓解：Y；触发：5min/30min
- 回滚：flag `xxx.enabled` 默认 false；错误率 > 1% 即回滚
- DoD：NFR P99 ≤ Xms；自检清单全勾
```

## 5 大场景职责矩阵

### 新增（Add）
- **核心职责**：从 0 到 1 引入新能力
- **典型输入**：需求描述、目标用户、依赖关系、性能与可用性预期
- **职责内必做**：新增模块的边界与对外契约、生命周期管理、是否复用现有能力的判断依据
- **明确不要做**：直接动业务代码、不给出对外契约就开始实施
- **输出物**：新增模块清单 + 边界图 + 对外契约 + 复用判定

### 修改（Change）
- **核心职责**：在已有能力上做演进
- **典型输入**：旧接口签名、调用方清单、迁移路径需求
- **职责内必做**：兼容性矩阵、迁移路径、废弃时间表
- **明确不要做**：直接破坏式重写、不通知调用方就改签名
- **输出物**：兼容性矩阵 + 迁移路径 + 废弃时间表

### 优化（Optimize）
- **核心职责**：在已有能力上做提升
- **典型输入**：当前基线指标、目标指标、优化空间估算
- **职责内必做**：基线+目标量化、灰度/回滚策略、可观测性埋点
- **明确不要做**：没有基线就开始优化、没有回滚策略就上生产
- **输出物**：基线/目标对照表 + 灰度方案 + 回滚策略

### 重构（Refactor）
- **核心职责**：在已有能力上做内部结构调整，**保持外部行为不变**
- **典型输入**：当前代码结构、外部行为契约、测试覆盖率
- **职责内必做**：行为不变性保证、分阶段拆分计划、双跑/灰度切流策略
- **明确不要做**：在重构中改外部行为、不做对比测试就切流
- **输出物**：行为不变性证据 + 拆分阶段表 + 双跑/灰度切流计划

### 移植（Port/Migrate）
- **核心职责**：把已有能力从一个项目搬到另一个项目
- **典型输入**：源项目模块边界、目标项目同名/相似模块、差异清单
- **职责内必做**：移植边界清单、一致性维度清单、本地化适配点、验证手段
- **明确不要做**：本地化适配不做记录、移植后不做对比验证
- **输出物**：移植边界清单 + 一致性维度清单 + 本地化适配记录

## 场景附加项

### 前端场景附加项

涉及前端/移动端 UI，必须追加：

- **UI 走查清单**：视觉一致性、交互对照、a11y
- **兼容性矩阵**：设备类型、系统版本、浏览器
- **性能指标**：FCP、LCP、TBT、CLS、首屏时间
- **国际化 / 本地化**：多语言文案、文案长度差异、RTL 适配

i18n 五项（任一不适用需显式写 `N/A + 原因`）：
- Key 命名：`<scope>.<feature>.<element>` 命名空间
- 复数 / 变量：ICU MessageFormat
- 文案长度预算：≥ +30% 源语言字符数
- RTL 与双向文本
- Fallback / locale 解析

### IoT / 边缘 / 离线优先场景附加项

涉及设备端、边缘节点、弱网或断网可用时，必须追加：

- **连接基线与状态机**：在线 / 弱网 / 断网 / 重连判定阈值
- **资源与断电恢复**：CPU、内存、磁盘、本地写入原子性、断电恢复点
- **离线数据与同步契约**：本地队列上限 / TTL、幂等键、重试退避
- **冲突策略**：服务端优先 / 设备端优先 / Last-Write-Wins
- **设备生命周期**：首次激活、OTA 分批、失败回滚
- **设备可观测性**：在线率、同步积压、同步失败率

## 边界条件

### 状态生命周期

方案文档按 `草稿 → 审核中 → 已批准 → 已发布 → 已归档` 管理；推荐方向失效时进入 `已撤回（Withdrawn）`，被替代时标记 `被取代（Superseded by <新方案名>）`，禁止静默覆盖或直接删除。

### 上线就绪检查

实施前必须确认 DoD、审批、风险与回滚 owner、Feature Flag、告警、回滚演练、灰度通知均已闭合。`HARD` DoD 100% 闭合才可实施，`SOFT` 项未完成需登记 owner 与到期日。

### 需要架构师评审的场景

| 触发条件 | 为什么 |
|----------|--------|
| 涉及核心架构调整 | 影响面大、可逆性差 |
| 跨 3 个以上团队协作 | 协调成本高 |
| 数据迁移 / Schema 变更 | 数据是核心资产 |
| 引入新核心依赖 | 供应链风险 |
| 涉及线上 SLO 调整 | 用户感知 |
| 估算 > 5 人日 | 复杂度高 |
| 涉及安全 / 合规 / 隐私 | 风险敞口大 |

### 方案评审分级与触发表

| 等级 | 触发条件 | 执行与证据 | 通过条件 |
|------|---------|-----------|---------|
| 必审 | 命中上表任一架构师评审条件 | 指定架构师全量评审并签字 | 明确"通过"且阻塞项为 0 |
| 抽审 | 未命中必审、也不满足免审全部条件 | `hash % 100 < 20` 时进入抽审 | 抽中则评审通过 |
| 免审 | 精简路径 + 单模块 + 预计 < 50 行 + 风险均为低 | 逐项记录免审条件证据 | 条件全部为真且证据齐全 |

## §精简路径

> 降级自 SKILL.md 旧版入口分流。命中条件全部满足时走此路径。

- **命中条件**：用户明确需要方案，范围已知、预计 < 50 行、单模块，且无数据/安全/合规/新依赖/跨服务影响（全部同时满足）
- **执行**：定向 Step 1；默认跳过三阶段（草稿→审核→优化）
- **产物**：5-10 行精简骨架
- **不可裁剪项**：NFR 量化、风险 owner、回滚触发条件

## §评审模式
