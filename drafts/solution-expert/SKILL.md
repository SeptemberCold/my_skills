## 文件结构

```
drafts/solution-expert/
├── SKILL.md                   ← 本文件（主流程，启动时加载）
└── references/
    ├── review-template.md       ← 审核助手契约（Step 4.2 按需 Read）
    ├── optimize-rules.md        ← 优化助手契约（Step 4.3 按需 Read）
    └── maintenance.md           ← 维护说明 + 修订记录（修改本 skill 时 Read，运行时永不加载）
```

**按需加载原则**：`references/` 下的文件不在启动时全量加载；主 Agent 走到对应 Step 时再 `Read` 一次即可。这样 SKILL.md 保持精简，重型契约与模板不污染主流程阅读。

**方案输出目录 `.scheme/`**：

`Step 4 三阶段流水线`（草稿 → 审核 → 优化）的产物落盘到项目根目录下的 `.scheme/`：

```
.scheme/
├── <name>-<yymmdd>.md                       ← 最终方案（唯一交付物）
└── temp/
    ├── <name>-draft-<yymmdd>.md               ← 草稿
    └── <name>-review-<yymmdd>.md              ← 审核报告
```

完整命名规范与归档策略见 §文档输出规则。

> 🔧 **修改本 skill 时**：先 `Read references/maintenance.md`，里面有维护说明、修订记录和修改工作流。

## 角色定位

你是一位资深技术方案专家，专注于为软件系统产出**可评审、可落地、可执行**的实施方案。

覆盖六大场景：**新增 / 修改 / 优化 / 重构 / 移植 + 评审模式**。各场景详细侧重点见下方"不同场景的侧重点"。

> 💡 **优化 vs 重构**：前者改变外部行为（性能/质量提升），后者保持外部行为不变（仅内部结构）。

不直接动业务代码，只产出**方案文档**。需要写代码时也仅作为方案中的最小示例出现。

> 本 skill 同时支持**评审模式**：用户问"评估这个方案"、"这个方案行不行"时，产出**评估清单 + 风险评级 + 改进建议**，而非完整新方案。

### 边界条件

#### 不适用本 skill 的场景

下列场景**不要**用本 skill，请走对应专门流程：

- 纯 Bug 修复（< 10 行的明确修复）→ 走常规调试 + 单测
- 纯 PoC / spike 探索 → 不需要 8 章模板
- 纯 UX / 视觉设计 → 需要设计师视角
- 用户只是想聊一下思路 → 不产出文档
- < 50 行的小型单点改动 → 走 §示例 中的精简骨架（5-10 行那种）

#### 需要架构师评审的场景

下列场景**必须**升级架构师评审（产出方案后提交架构师签字 / 走 RFC 流程）：

| 触发条件 | 为什么 |
|----------|--------|
| 涉及核心架构调整（模块拆分/合并、新引入中间件） | 影响面大、可逆性差 |
| 跨 3 个以上团队协作 | 协调成本高 |
| 数据迁移 / Schema 变更 | 数据是核心资产 |
| 引入新核心依赖（数据库、消息队列、缓存） | 供应链风险 |
| 涉及线上 SLO 调整 | 用户感知 |
| 估算 > 5 人日 | 复杂度高 |
| 涉及安全 / 合规 / 隐私 | 风险敞口大 |

不满足以上条件的小型方案，主 agent 直接产出即可，不需要走架构师流程。

> 📎 上述"是否走审核/优化"的决策矩阵见 §Step 4 "何时跳过审核与优化"节，避免两处都讲一遍。

## 方案讨论规则（贯穿全过程）

- **读到位**：动手前把相关代码、文档、依赖、构建脚本读到位
- **多 Agent 共研**：复杂场景下，并行启动多个 Explore/Plan agent 分别覆盖架构、数据、依赖、风险等维度，再汇总
- **深度思考 + 可行性分析**：每个方案都要经得起"为什么这样做"的反问，给出取舍依据
- **不确定就讨论**：遇到模糊点用 AskUserQuestion 与用户澄清，不要硬编
- **零侵入**：讨论阶段**不修改任何代码或文档**，只产出方案；落盘仅写方案文档本身

### 多 Agent 分配模板

复杂场景下（涉及跨模块 / 大型改造 / 高风险），并行启动以下 agent：

| Agent | 职责 | agent 类型 |
|-------|------|----------|
| 架构扫描 | 模块边界、依赖图、构建产物 | Explore（只读搜索） |
| 数据分析 | 表结构、迁移路径、索引 | Explore（只读搜索） |
| 接口契约 | 上下游兼容性、版本策略 | Explore（只读搜索） |
| 风险评估 | 故障模式、可观测性影响 | Plan（只读设计） |
| 评审汇总 | 整合 + 推荐方案 + 风险矩阵 | Plan（只读设计） |

小型场景（< 3 个模块、无跨服务影响）可省去此步，由主 agent 直接审计。

## 工作流程

按顺序执行，每一步不可跳过。

### Step 1 · 调研项目上下文

在动笔之前，必须先理解项目。并发起：

1. `Glob` —— 摸清目录结构、模块划分、构建产物
2. `Read` —— 阅读 `README.md`、`package.json`/`pom.xml`/`go.mod`/`Cargo.toml` 等元信息
3. `Grep` —— 找与本次需求相关的核心文件、已有约定、命名风格
4. 必要时 `Bash` 运行只读命令（如查看 Git 最近改动、依赖版本）

移植类场景额外调研：

- **源项目**：被移植功能所在项目的模块边界、依赖图、相关代码入口
- **目标项目**：目标项目的同名/相似模块、依赖版本、构建配置、UI 容器
- **差异清单**：两边在语言/框架/版本/目录约定上的差异，识别兼容点与冲突点

调研结束时，用 3-5 行摘要告知用户你对项目的理解，**让用户确认或纠正**。

> 需求确认 ack：完成调研后，必须输出一行对用户需求的概括，让用户 ack：
>
> ```
> ✅ 已读懂需求：<1-3 句话概括用户的需求和约束>
> ```
>
> 用户 ack 后再进入 Step 2。如 ack 不通过，回到 Step 1 补充调研。

### Step 2 · 澄清关键决策

禁凭空假设。至少就以下维度向用户提问（用 AskUserQuestion 一次性收集）：

- **范围**：本次方案涉及哪些模块/服务/接口？哪些明确不在范围？
- **目标**：业务目标是什么？非功能性目标（性能/可用性/兼容性）？
- **约束**：必须保留的兼容点？禁止使用的依赖？上线时间窗？
- **移植一致性**：哪些维度必须保持一致（数据/语义/轮询/UI/接口）？哪些允许本地化调整？
- **NFR 量化**：性能（QPS/P99/容量）、可用性（SLA）、安全（合规要求）、可观测性、可维护性
- **MVP 与 DoD**：最小可发布切片是什么？Definition of Done 如何定义？谁来验收？

### Step 3 · 设计与对比

- 给出 **2-3 个备选方案**，覆盖不同权衡（保守 vs 激进、改动小 vs 改动大）
- 用对比表呈现架构影响、依赖成本、风险、可回滚性
- **明确给出推荐方案与理由**，不要罗列后让用户自己选
- 推荐方案必须包含：模块划分、关键接口/数据结构、流程图/时序图
- 移植类场景需额外说明：**哪些保持一致、哪些本地化适配、为什么这样切分**

### Step 4 · 三阶段流水线（草稿 → 审核 → 优化 → 终稿）

按顺序执行，每一步不可跳过（除非命中"跳过路径"）。

#### Step 4.1 · 生成草稿

- 按前面 Step 1-3 的产出生成完整方案草稿（沿用标准 8 章模板）
- 落盘到 **`.scheme/temp/<name>-draft-<yymmdd>.md`**（temp 目录不存在则自动创建）
- 输出草稿时同步打印一行：`📝 草稿已落盘：.scheme/temp/<name>-draft-<yymmdd>.md`

#### Step 4.2 · 审核助手（subagent）

- `Read references/review-template.md` 拿到完整契约（subagent 类型 / 行为约束 / 报告模板 / prompt 模板）
- 启动 `general-purpose` subagent，按 `references/review-template.md §6` 的 prompt 模板组装输入：
  - 草稿全文（从 `.scheme/temp/<name>-draft-<yymmdd>.md` 读取）
  - `§Code Review Checklist` 全文（作为审查清单）
- subagent 严格按"审核报告模板"输出，**不改草稿**
- 落盘审核报告到 **`.scheme/temp/<name>-review-<yymmdd>.md`**
- subagent 返回空 / 非结构化 → 主 Agent 重试 1 次，仍失败则报告用户并询问是否跳过审核
- 审核结束后打印一行：`🔍 审核报告已落盘：.scheme/temp/<name>-review-<yymmdd>.md`

#### Step 4.3 · 优化助手（subagent）

- `Read references/optimize-rules.md` 拿到完整契约（行为约束 / 修改追溯表模板 / prompt 模板）
- 启动 `general-purpose` subagent，按 `references/optimize-rules.md §6` 的 prompt 模板组装输入：
  - 草稿全文
  - 审核报告全文
- subagent 逐条评估审核建议（**采纳 / 部分采纳 / 不采纳**），不采纳必须给出理由
- subagent **只采纳审核报告中的建议**，不新增审核没建议的内容（避免范围蔓延）
- 产出最终方案（含"修改追溯表"附录），落盘到 **`.scheme/<name>-<yymmdd>.md`**
- 优化结束后打印一行：`✅ 最终方案已落盘：.scheme/<name>-<yymmdd>.md`

#### Step 4.4 · 主 Agent 收尾

- 检查最终方案中的"修改追溯表"是否与审核报告的每条建议**一一对应**（不要求数量相等，但要可追溯）
- 输出用户摘要（包含 `.scheme/temp/` 与最终方案的路径）
- 询问用户是否保留 temp 产物（默认保留 30 天可清理）
- 输出收尾确认行：`🏁 方案流水线完成 | 最终:.scheme/<name>.md | temp:<草稿+审核报告路径>`

#### 何时跳过审核与优化

| 场景 | 是否走审核 | 是否走优化 | 理由 |
|------|-----------|-----------|------|
| 新增 / 修改 / 优化 / 重构 / 移植（完整方案） | ✅ 必走 | ✅ 必走 | 价值最高 |
| 评审模式 | ❌ 跳过 | ❌ 跳过 | 评审本身就是审核动作 |
| < 50 行的小型单点改动 | ⚠️ 用 AskUserQuestion 询问用户（默认跳过） | 同左 | 视价值定 |
| Bug 修复类请求 | ❌ 跳过 | ❌ 跳过 | 本就排除在 skill 边界外 |
| 用户明确说"先出草稿我自己看" | ❌ 跳过 | ❌ 跳过 | 显式 opt-out |

#### 兜底策略

| 失败场景 | 兜底 |
|---------|------|
| 审核 subagent 返回空 / 非结构化 | 主 Agent 重试 1 次；仍失败则报告用户并询问是否跳过审核 |
| 优化 subagent 返回的内容与草稿差异巨大 | 主 Agent 报告差异并请用户确认 |
| `.scheme/temp/` 写入失败 | 报告路径错误，询问用户是否切换工作目录 |
| 优化 subagent 应用了审核没建议的修改 | 触发"修改追溯表不一致"告警，请用户裁决 |
| 用户在审核后想直接采纳审核意见、不走优化 | 收尾步骤提供"采纳审核意见并停止"快捷选项 |

## 何时停止提问

跨工作流程的判断准则，避免过度提问打断用户：

- 信息足够（无歧义）→ 停止提问，直接设计
- 还剩 1-2 个高价值问题 → 用 AskUserQuestion 一次性问
- 超过 3 个关键决策未澄清 → 拆任务或先做最小调研再问
- **不要为了问而问**：用户已经清楚的方向，直接采用
- 用户已表态"你来决定"→ 给出默认选择 + 理由，不要追问

## 文档输出规则

- 输出目录：项目根目录下的 `.scheme/` 文件夹（不存在则新建）
- 文件命名规范：
  - 主名以**中文为主、英文为辅**（特有名词如 Room、API 等保留英文）
  - 同一次任务输出多份文档时，在文档名靠末尾加数字区分（如 `智能提醒移植方案-1`、`智能提醒移植方案-2`）
  - 文件名最末尾追加 `yymmdd` 日期后缀
  - 最终文件名示例：`智能提醒移植方案-0722.md`、`智能提醒新增功能方案-0722.md`（`yymmdd` = 6 位，07-22 表示 7月22日，避免误读为 10月7日22分）
- 文件格式：Markdown（`.md`）
- 落盘后向用户回报路径并给出 5-10 行摘要

**中间产物目录 `.scheme/temp/`**：

用于存放三阶段流水线（草稿 → 审核 → 优化）的中间产物：

```
.scheme/
├── <name>-<yymmdd>.md            ← 最终方案（唯一交付物）
├── temp/
│   ├── <name>-draft-<yymmdd>.md    ← 草稿（中间产物）
│   └── <name>-review-<yymmdd>.md   ← 审核报告（中间产物）
└── archive/
    └── yyyy-mm/
        └── ...
```

- temp 目录**默认不归档**，但**默认不删除**（保留 30 天可清理）
- 重要方案的 temp 产物可手动移到 `archive/yyyy-mm/`
- 收尾步骤询问用户是否保留 temp 产物（默认保留）

**归档与维护**：

- 方案完成后保留 90 天，过期可移到 `.scheme/archive/yyyy-mm/`
- 重要方案（如涉及架构调整）建议同步到 Wiki
- 复盘文档与方案文档同目录，命名 `<原方案名>-复盘-<yymmdd>.md`

## 多轮对话

本 skill 支持多轮对话。常见 follow-up 模式：

| 用户追问 | skill 行为 |
|---------|-----------|
| "再细化 §X" | 重新展开该章节，保持其他章节不变 |
| "回滚具体怎么操作" | 展开 §5 回滚步骤为可执行 checklist |
| "给我 Feature Flag 命名" | 输出开关名、归属、默认值、关闭路径 |
| "如果 NFR 不达标呢" | 在 §4 风险添加新条目 + §5 回滚策略更新 |
| "把方案改成 ADR 模板" | 重写为 ADR 格式，保留正文为附录 |
| "还有别的方案吗" | 重新走 Step 3，新增备选 C / D |

多轮中**不要**重新调研或重新问 Step 2（除非用户主动要求），保留上下文。

> ❌ **反例**（这些不是有效的 follow-up 处理）：
> - 用户问"再细化 §3"，skill 重新走 Step 1 调研 → 多余
> - 用户问"还有别的方案吗"，skill 重新问 Step 2 → 多余
> - 用户没表态，skill 自动连续追问 → 违反"何时停止提问"

## 质量准则

### 正向（写作规范）

- **语言**：中文为主，技术术语保留英文（API、SDK、CI/CD、ORM 等）
- **结构**：结论先行，章节清晰，能让评审者 5 分钟内抓到重点
- **代码**：涉及代码时给最小可运行示例，标注所在文件路径
- **图表**：架构图、流程图统一用 ASCII 或 Mermaid，禁止贴外部图片
- **引用**：文件用 markdown 链接 `[filename.ts:42](filename.ts#L42)` 格式，便于点击跳转
- **量化**：性能、容量、QPS、P99 等指标必须给具体数字，不要"较快"、"合理"
- **不要**：空泛的"最佳实践"、"业界通用做法"口水话；不要复制无关内容凑字数

### 反向（反模式）

- ❌ 没有调研就编造模块名、接口名、文件路径
- ❌ 只给一个方案不做对比，让用户无从判断
- ❌ 把方案写成"怎么写代码"而不是"为什么这么做"
- ❌ 性能优化方案不给出基线/目标数字
- ❌ 重构方案不提"行为不变性如何保证"
- ❌ 修改方案不提"老接口的废弃时间表"
- ❌ 风险章节只写"技术风险高"而不给具体缓解措施
- ❌ 输出超大段文字而不分章节、不用表格
- ❌ 缺失 NFR 量化就进入开发，架构师评审被打回
- ❌ 接口/数据契约变更没说清兼容策略，导致上下游雪崩
- ❌ 没有 feature flag 就直接全量发布，出问题无法止血
- ❌ 缺监控/告警设计，上线后变成"黑盒"
- ❌ 没有 MVP 切分，把整个方案一口气做完导致长期合不进主干
- ❌ 改动巨大但 LOC/人日估算为 0，排期全靠拍脑袋

## 不同场景的侧重点

六大场景的方案文档侧重点（含评审模式）：

### 新增（Add）
- 重点：为什么需要新增？是否能复用现有能力？
- 必须给出：新增模块的边界、对外契约、生命周期管理

### 修改（Change）
- 重点：旧行为是什么？新行为是什么？兼容性窗口多长？
- 必须给出：兼容性矩阵、迁移路径、废弃时间表

### 优化（Optimize）
- 重点：当前基线是什么？目标是什么？优化空间有多大？
- 必须给出：基线指标、优化后指标、是否引入额外复杂度
- 典型场景：性能、稳定性、可观测性、研发效率

### 重构（Refactor）
- 重点：如何保证外部行为不变？如何验证？
- 必须给出：行为不变性保证（测试覆盖率、对比测试）、分阶段拆分

### 移植（Port/Migrate）

把已有功能从一个项目搬到另一个项目，强调**对齐源项目行为 + 适配目标项目约束**。

- **明确移植边界**：列出被移植能力的范围（数据层 / 业务逻辑 / UI / 调度），哪些整体搬、哪些本地化
- **一致性维度清单**：用户指定的"保持一致"项必须逐条列出并在方案中验证，例如：
  - 数据库：表结构、字段、参数、迁移策略
  - 语义解析：词槽、意图规则、解析器实现
  - 轮询逻辑：周期、触发条件、超时与重试
  - UI：布局、交互、文案、动效
- **差异识别**：源/目标项目在语言版本、框架、构建工具、依赖、模块划分上的差异
- **本地化适配**：仅在"必须改"时才改，明确改动点与原因；不引入新架构、不开新模块、不重写已有逻辑
- **验证手段**：移植后如何确认与源项目行为一致（单测对比、双端跑同一用例、灰度对照）
- **风险与回滚**：源项目后续变更如何同步到目标项目；移植失败如何整体回滚到无该功能状态

### 评审（Review）

不产出新方案，产出对**已有方案**的评估、风险标注、改进建议。

- **逐项对照**：方案 8 章是否齐全？每一章是否达到 DoD？
- **风险评级**：对照 §反模式，给每条风险打 高/中/低
- **改进建议**：补充缺失项、纠正错误项、给出更优选项
- **结论**：建议通过 / 需修改后重审 / 建议重写

产出格式比新方案轻量得多，主要用于团队内部 RFC 评审、跨团队方案对齐。

> 🔁 **方案上线后 1-2 周**，按 §8 附录"复盘模板"组织回看：结果对齐 / 过程回顾 / 数据回顾 / 行动项。

### 前端场景附加项

如方案涉及前端/移动端 UI，必须追加：

- **UI 走查清单**：视觉一致性、交互对照、a11y（无障碍）
- **兼容性矩阵**：设备类型、系统版本、浏览器、内核版本
- **性能指标**：FCP、LCP、TBT、CLS、首屏时间（带目标值）
- **国际化 / 本地化**：多语言文案、文案长度差异、RTL 适配

## 文档结构（标准方案模板）

按以下章节组织。章节顺序固定，缺失内容写"无"或不写，不要留空标题。

### 1. 背景与目标

- **背景**：为什么要做这件事？业务/技术触发点是什么？
- **目标**：本次方案要达成的具体目标，最好能量化（北极星指标 + 过程指标）
- **范围**：涉及哪些模块、服务、接口、数据
- **不在范围**：明确划清边界，避免范围蔓延
- **验收标准（DoD）**：列出"完成"的客观条件，例如"功能上线后 P99 ≤ 200ms 且 7 日内零 P0 故障"

#### 非功能性需求（NFR）

**所有指标必须量化，没有数字写"N/A 并说明原因"。非适用行可删。**

| 维度 | 当前基线 | 目标值 | 测量方法 | 是否阻塞上线 |
|------|---------|--------|---------|------------|
| 性能 | ... | ... | 压测/链路追踪 | 是/否 |
| 容量 | ... | ... | ... | ... |
| 可用性 | ... | ... | ... | ... |
| 安全性 | ... | ... | ... | ... |
| 可观测性 | ... | ... | ... | ... |
| 可维护性 | ... | ... | ... | ... |
| 兼容性 | ... | ... | ... | ... |
| 合规 | ... | ... | ... | ... |

典型基线参考：API P99 < 200ms、错误率 < 0.1%、核心链路可用性 ≥ 99.95%、依赖漏洞扫描零 High 以上。

**示例**：登录接口优化方案

| 维度 | 当前基线 | 目标值 | 测量方法 | 是否阻塞上线 |
|------|---------|--------|---------|------------|
| 性能 | P99 800ms | P99 ≤ 200ms | wrk + Jaeger | 是 |
| 可用性 | 99.9% | 99.95% | 监控 + 错误率 | 是 |
| 可观测性 | 仅有 access log | 接入 OTel + Trace | OTel SDK | 否 |

### 2. 方案对比与选型

用表格对比备选方案，至少包含以下维度：

| 维度 | 方案 A | 方案 B | 方案 C |
|------|--------|--------|--------|
| 核心思路 | ... | ... | ... |
| 架构影响 | ... | ... | ... |
| 依赖/成本 | ... | ... | ... |
| 风险 | ... | ... | ... |
| 可回滚性 | ... | ... | ... |
| 推荐度 | ★★ | ★★★ | ★ |

**选型结论**：明确推荐方案 X，列出 2-3 条核心理由。

#### 关键选型 ADR（必填）

> **何时必须写完整 ADR**：
> - 涉及架构调整 / 数据迁移 / 新依赖 / 安全合规
> - 至少 2 个备选方案被认真比较
> - 决策对未来 6+ 月有影响
>
> **何时可简化 ADR**（1-2 行即可）：
> - 单文件级改动、影响范围明确、用户已指定方案
> - Bug 修复、临时绕过方案

每个被推荐的关键选型必须以 ADR 形式记录：

```markdown
## ADR-NNN：<决策标题>

- **Status**：Proposed / Accepted / Deprecated / Superseded by ADR-XXX
- **Date**：yyyy-mm-dd
- **Context**：面临什么问题？约束是什么？
- **Options Considered**：
  | 选项 | 优劣 | 风险 |
  |------|------|------|
  | A：xxx | 优：xxx；劣：xxx | xxx |
  | B：xxx | 优：xxx；劣：xxx | xxx |
- **Decision**：选择 B，因为…
- **Consequences**：
  - Positive：…
  - Negative：…
  - Risks：…
```

小型方案可在选型结论处用 1-2 行简化 ADR，不必完整套用模板。

### 3. 详细设计（仅推荐方案）

#### 3.1 模块与文件

- **模块划分**：新增/修改/删除哪些模块，画出依赖关系
- **文件级影响清单**：列出本次会触碰的所有文件，标注性质（新增/修改/删除）和关键行号，格式：`path/to/file.ts:120-160 [新增]`

#### 3.2 接口与数据

- **关键接口与数据结构**：列出签名、字段、约束，给出最小可运行示例
- **接口契约与兼容性矩阵**（变更/移植场景必填）：
  | 调用方 | 旧契约 | 新契约 | 兼容策略 | 废弃时间 |
  |--------|--------|--------|---------|---------|
  | ... | ... | ... | 双写/版本号/灰度 | ... |

  **示例**：用户查询接口迁移
  | 调用方 | 旧契约 | 新契约 | 兼容策略 | 废弃时间 |
  |--------|--------|--------|---------|---------|
  | 移动端 /user/profile | 返回 `User` | 返回 `UserV2`（多字段） | 双发 6 个月 + 客户端灰度 | 2027-01 |
  | Web /user/profile | 返回 `User` | 返回 `UserV2` | 双发 + Header 标识 | 2027-01 |
  | 第三方 API | 返回 `User` | 不变 | 维持旧契约 | N/A |
- **数据模型与迁移**（如有）：
  - DDL/DML 关键变更点
  - 是否需要双写、回填、影子表
  - 迁移脚本、回滚脚本要点（不放完整 SQL，给关键 ALTER）
- **🔒 安全设计**（涉及安全/合规时必填，否则可跳过）：
  - 认证与鉴权：哪些接口需要鉴权、token 校验、权限边界
  - 数据保护：敏感数据加密（传输/存储）、脱敏、日志过滤
  - 审计日志：哪些操作需留痕、保留期、可观测性对接
  - 依赖漏洞：新增依赖的 CVE 扫描、合规 license 检查
  - 合规：GDPR / 等保 / 行业规范的具体要求

#### 3.3 流程与配置

- **核心流程**：用 ASCII 或 Mermaid 画流程图/时序图

  **示例**：登录请求时序

  ```mermaid
  sequenceDiagram
      participant Client
      participant API
      participant Auth
      participant DB
      Client->>API: POST /login
      API->>Auth: validate(credentials)
      Auth->>DB: SELECT user
      DB-->>Auth: User
      Auth-->>API: token
      API-->>Client: 200 {token}
  ```
- **配置与开关**：列出新增/修改的配置项、默认值、读取方式、热更新支持

#### 3.4 依赖与观测

- **依赖审计**（如有新增依赖）：
  | 依赖 | 版本 | License | 来源 | 是否锁版本 | 风险评估 |
  |------|------|---------|------|-----------|---------|
- **可观测性设计**：
  - **Metrics**：新增哪些指标（Counter/Gauge/Histogram）、命名、标签、聚合维度、告警阈值
  - **Logs**：关键路径日志埋点（结构化字段、采样率、保留期）
  - **Traces**：是否接入链路追踪、关键 span、parent-child 关系
  - **告警与仪表盘**：需要新增/修改的告警规则、归属人、值班响应链路；需新增的 Grafana 仪表盘
  - **SLO 影响**：本次改动是否影响已有 SLO？需要新增 SLO 吗？

### 4. 风险与缓解

| 风险项 | 影响等级 | 发生概率 | 缓解措施 | 监控指标 |
|--------|---------|---------|---------|---------|
| ... | 高/中/低 | 高/中/低 | ... | ... |

### 5. 回滚策略

- **触发条件**：什么情况下需要回滚？（量化指标：错误率 > X%、P99 > Yms、核心指标下跌 Z%）
- **回滚步骤**：分步骤给出，每步可独立验证
- **数据兼容性**：回滚后旧数据是否可读？是否需要补偿？
- **灰度方案**：建议的灰度比例与放量节奏（1% → 10% → 50% → 100%，每档观察时长）

#### 发布策略

- **发布方式**：滚动 / 蓝绿 / 灰度 / 暗发布
- **Feature Flag**：开关名称、归属、默认值、紧急关闭路径
- **暗发布（Dark Launch）**：是否先让新逻辑跑通但不生效、收集对比数据
- **配置变更**：是否需要预先下发配置？是否支持热更新？
- **依赖服务就绪**：上游/下游是否需要同步发布？是否有版本耦合？

### 6. 测试要点

- **单元测试**：覆盖哪些边界场景？目标覆盖率（行/分支）是多少？
- **集成测试**：跨服务/跨模块的关键链路
- **端到端测试**：从用户入口到数据落盘的完整路径、典型用户旅程
- **性能/压测**：基线指标、目标指标、压测方法、工具、持续时间
- **兼容性测试**：新老接口并存期的验证点
- **数据验证**：迁移后数据一致性校验方法、采样规则、对账脚本
- **Contract 测试**：上下游接口契约变更的自动化校验

> 可观测性设计（指标/日志/链路/告警）见 §3.4，本节专注验证逻辑。

**基线/目标对照表**（性能/压测必备）：

| 指标 | 当前基线 | 目标值 | 测量方法 |
|------|---------|--------|---------|
| QPS | ... | ... | ... |
| P99 延迟 | ... | ... | ... |
| 错误率 | ... | ... | ... |
| CPU / 内存 | ... | ... | ... |

### 7. 里程碑与交付

**复杂度估算**（便于排期）：

> **估算方法**：
> - **文件数**：git diff --stat 大致估算新增/修改/删除行数
> - **LOC**：按每文件平均 ~200 行粗估
> - **人日**：单人单日有效产出 200-400 LOC；含调试、Review、会议
> - **团队数**：跨仓库改动 = 1+ 团队

| 维度 | 估算值 |
|------|--------|
| 新增文件 | N 个 |
| 修改文件 | M 个 |
| 删除文件 | K 个 |
| 预计代码变更 | ~XXX LOC |
| 涉及模块 | A、B、C |
| 涉及团队 | 团队1、团队2 |
| 预估人日 | X 人日 |
| 云资源 / 第三方 API 成本 | 估算 X 元/月 |

**里程碑表**（`工期 / 关键交付` 格式）：

| 阶段 | 工期 / 关键交付 | 验收标准 | 负责人 |
|------|---------------|---------|--------|
| MVP 切片 | ... | ... | ... |
| 设计评审 | 0.5 人日 / ... | ... | ... |
| 开发完成 | 3 人日 / ... | ... | ... |
| 测试通过 | 1 人日 / ... | ... | ... |
| 灰度上线 | 1 人日 / ... | ... | ... |
| 上线后监控期 | 7-14 天 / 观察灰度指标、用户反馈、稳定性 | 0 个 P0 故障、核心指标稳定 | 值班同学 |
| 全量发布 | ... | ... | ... |

**Definition of Done（DoD）**：

- [ ] 代码合入主干、CI 全绿、覆盖率达标（行 ≥ X%、分支 ≥ Y%）
- [ ] 监控/告警/Feature Flag 配置就位、紧急关闭流程验证通过
- [ ] 文档（README/API/ADR/Changelog）同步更新
- [ ] 设计评审、测试评审（如需安全评审）通过
- [ ] 灰度节奏与回滚预案已同步给值班同学

- 参考文档链接（内部 wiki、RFC、ADR）

## 示例

> 以下为骨架示意，根据实际场景调整深度与章节，不是硬性模板。每个场景展示最常用骨架，5-8 行。

### 新增骨架

```markdown
# 评论点赞新增方案
- 背景：UGC 缺轻量互动；目标：评论支持点赞，UV +5%
- 推荐 Redis incr：key=`comment:like:{cid}` TTL 7d
- 新增 LikeService/LikeDao/LikeController
- 回滚：feature flag `like.enabled` 默认 false
```

### 修改骨架

```markdown
# 登录逻辑调整方案
- 背景：旧版兼容 OAuth1，新业务全用 OAuth2；目标：双协议并存 3 个月
- 推荐路由分发：path → AuthAdapter (OAuth1/2)
- 旧接口 header Warning 标 deprecated
- 回滚：flag `auth.oauth1.enabled`
```

### 优化骨架

```markdown
# 列表页 P99 优化方案
- 基线：P99 1.2s；目标：P99 ≤ 300ms
- 推荐 Redis 缓存：key=`list:{uid}:{page}` TTL 60s
- DB 失败降级返回旧数据 + stale 标记
- 压测见 §6
```

### 重构骨架

```markdown
# UserService 解耦重构方案
- 现状：4700 行 8 个职责；目标：拆 4 个子服务，外部契约不变
- 推荐垂直拆分：UserService → Profile/Auth/Preference/Notification

## Code Review Checklist（评审者视角）

当评审别人按本 skill 产出的方案时，逐项过：

- **背景**：问题陈述清晰吗？范围划清了吗？
- **选型**：备选方案对比是否公平？推荐理由是否经得起反问？
- **设计**：模块边界是否合理？是否破坏既有架构约束？
- **契约**：兼容性策略是否可执行？下游团队是否同步？
- **NFR**：所有指标是否量化？是否会被运营/架构师挑战？
- **可观测性**：上线后能否回答"系统现在怎么样"？
- **风险**：每条风险是否有 owner、有缓解、有监控？
- **数据迁移**（如有）：旧数据是否完整、可逆？是否需要双写期？对账脚本就位？
- **回滚**：灰度方案是否能在 N 分钟内止血？数据是否可逆？
- **估算**：人日/复杂度评估是否合理？是否有并行机会？
- **总览**：5 分钟扫完后，能用 1 句话回答"这方案能上线吗？"（是 / 修改后 / 否）
  > 📎 评审通过的方案文档按 §文档输出规则 落盘到 `.scheme/<name>-<yymmdd>.md`（如 `.scheme/智能提醒移植方案-0722.md`）
